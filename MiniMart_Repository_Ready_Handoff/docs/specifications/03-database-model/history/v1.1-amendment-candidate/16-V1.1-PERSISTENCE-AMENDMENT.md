# v1.1 Persistence Amendment

## 1. Design rule

The amendment stores only already-frozen business meaning. It does not
use database design to decide OPEN/VERIFY/DEFERRED policy.

## 2. Item and UoM identity

`catalog.item_uoms.item_uom_id` is the stable API-facing UoM identity.\
`is_base`, `is_sales_default`, and `is_purchase_default` define the
Item-specific role. Partial unique indexes allow at most one active role
row per Item. The application must ensure the selected role row belongs
to the same Item and is operationally valid.

`catalog.items.base_uom_code` is retained for v1.0
compatibility/migration evidence. v1.1 API contracts should use the
Item-UoM UUID identities. A later cleanup may remove the legacy code
only through reviewed migration.

`quantity_precision` belongs to Item-UoM. An Item-level API convenience
field, if retained, must be explicitly derived from the selected
sales/base UoM rather than stored as a second authority.

## 3. Batch and expiry

`batch_tracked` and `expiry_tracked` become explicit master attributes.
The v1.0 `tracking_policy` column is retained only as migration
compatibility evidence and must not become an independently editable
second source of truth.

## 4. Identifiers and contacts

Company, Supplier and Customer identifiers are repeatable child rows so
country/business identifiers are not forced into one universal field.
Legacy single `tax_identity` columns remain migration-compatible but are
not sufficient for new v1.1 writes.

Supplier contacts are repeatable child rows because the FRS explicitly
supports multiple named contacts/purposes.

## 5. Pricing

Reference/maximum/recommended price remains nullable and contextual.
`reference_price_kind` and `tax_price_context_code` do not assert any
country-specific legal value. Country packs remain authoritative for
applicability.

## 6. Credit

`credit_limit_mode` supports an explicit fixed/no-fixed-limit state
without encoding an arbitrary huge number. `terms_code` and
`due_date_basis_code` persist the configured credit-term basis.
Held-sale pending exposure is intentionally not persisted because its
treatment remains an OPEN decision.

## 7. Return reason

Return reason/note can exist at header and/or line level. Posting
validation decides which level is required by configured policy; the
database does not invent that policy.

## 8. Infrastructure boundaries

Store Node enrollment/credential association remains an
architecture/infrastructure concern. It is not added to `org.stores`.
Session/device credential storage requires its own technical persistence
decision if durable storage is later required.

## 9. Migration safety

The forward migration adds nullable columns first where an existing
installation would require backfill. NOT NULL enforcement shown in the
v1.1 reference DDL is permitted only after authoritative backfill and
verification. No migration may infer OPEN policy values.
